# Общий принцип

Vault выступает централизованным хранилищем секретов. Все сервисы и приложения получают доступ только через авторизованные механизмы: Kubernetes Auth, GitHub OIDC, CI/CD pipelines. Секреты не хранятся в Git или контейнерах напрямую.

# Этапы

1. **Инициализация Vault**  
   - Создание корневого токена и unseal ключей  
   - Настройка движков (KV, Database, Transit)  

2. **Загрузка секретов**  
   - Секреты создаются или импортируются в Vault через CLI или API  
   - Примеры: `database.json`, `api-keys.json`, `tls-certificates.json`  

3. **Настройка политик и ролей**  
   - Определение прав доступа через `policies/`  
   - Назначение ролей приложениям и CI/CD через `roles/`  

4. **Интеграция с приложениями**  
   - Backend и frontend получают секреты через маппинг (`backend-secret-mapping.yaml`, `frontend-secret-mapping.yaml`)  
   - CI/CD pipelines используют скрипты авторизации (`vault-auth-github-actions.sh`)  

5. **Runtime доступ**  
   - Vault Agent Injector или External Secrets Controller подтягивает секреты в поды  
   - Шифрование на лету через Transit Engine  

6. **Ротация и управление секретами**  
   - Скрипты: `rotate-secrets.sh`, `rotate-root-token.sh`, `rotate-unseal-keys.sh`  
   - Автоматические бэкапы через `backup.sh` и восстановление через `restore.sh`  

# Потоки данных между компонентами

- **CI/CD → Vault**: получение токена → чтение секрета → использование в пайплайне  
- **Backend/Frontend → Vault**: запрос секрета → Vault Agent/External Secrets → переменная окружения/файл  
- **Observability**: метрики и алерты собираются из Vault через Prometheus/Grafana  
- **Auth systems**: Keycloak или GitHub OIDC передают JWT → Vault проверяет политику доступа  

# Принцип единого источника

Все секреты централизованы в Vault, ни один сервис не хранит секреты локально или в Git. Все операции логируются в Audit Engine для контроля и аудита.
