## Цель

Документ описывает архитектуру High Availability (HA) для Vault в проекте **health‑api**, обеспечивая отказоустойчивость, масштабируемость и непрерывный доступ к секретам.

---

## Компоненты HA

* **Vault Primary Node** — основная нода кластера, принимает записи и управляет логикой репликации.
* **Vault Secondary Nodes** — реплики, поддерживающие чтение секретов и готовые к промоушену в случае падения Primary.
* **Consul/RAFT Backend** — хранилище метаданных кластера, обеспечивает синхронизацию состояния между нодами.
* **Load Balancer** — маршрутизирует трафик между нодами Vault, обеспечивает доступность API для приложений.
* **Vault Clients** — приложения и CI/CD-пайплайны, использующие Vault Agent или External Secrets для безопасного получения секретов.

---

## Репликация и кластеризация

* Используется **Integrated Storage (Raft)** для HA, каждая нода хранит лог транзакций.
* Конфигурация `vault.hcl` содержит секции:

```hcl id="raft-example"
storage "raft" {
  path    = "/opt/vault/data"
  node_id = "vault-node-1"
}
listener "tcp" {
  address     = "0.0.0.0:8200"
  tls_cert_file = "/opt/vault/tls/vault.crt"
  tls_key_file  = "/opt/vault/tls/vault.key"
}
ha_enabled = true
```

* Primary Node обрабатывает запись; Secondary Nodes получают обновления через Raft.
* При падении Primary Secondary Node может быть повышена через `vault operator step-down`.

---

## Балансировка и доступность

* Используется **Layer 4/Layer 7 Load Balancer** (HAProxy/Nginx/Cloud LB).
* LB распределяет запросы между нодами Vault, направляя write-запросы к Primary.
* TLS и mTLS применяются для шифрования между клиентами и нодами.
* External Secrets или Vault Agent Injector работают с LB и автоматически перенаправляют на доступную ноду.

---

## Мониторинг и восстановление

* **Prometheus** собирает метрики Vault: доступность, задержки, количество запросов.

* **Grafana** визуализирует состояние кластера и предупреждения.

* **Falco/Trivy** следят за runtime-безопасностью контейнеров Vault.

* **Disaster Recovery:**

  * Unseal ключи распределены между администраторами
  * Регулярные snapshots сохраняются для восстановления
  * При полной потере Primary ноды Secondary может стать новой Primary, используя snapshot или Raft лог

* Регулярно тестировать failover и восстановление из snapshot на dev/staging окружении.
